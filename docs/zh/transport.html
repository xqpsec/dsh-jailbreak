fetch 改了 body，发出去还是原文

这是过去两个月里最坑的一个问题，也是插件 1.3.6 的核心修复。它的症状有欺骗性：

  • 日志写 changed:true；
  • 审计记录里 mode 也对；
  • 抓包一看，上游收到的还是原始请求体。

返回值层面看不出任何异常，因为改写函数确实返回了 changed:true，只是那个新 body 从来没被发出去。

一、最小复现

const original = globalThis.fetch;

globalThis.fetch = async function (input, init) {
  const req = new Request(input, init);
  const body = await req.json();          // {model, messages:[…]}
  body.messages[0].content = 'REWRITTEN';

  // ❌ 看起来合理，实际无效
  const next = new Request(req.url, req, { body: JSON.stringify(body) });
  return original.call(this, next);
};

抓包结果：上游收到的 messages[0].content 还是 REWRITTEN 之前的值。

二、原因：构造器只有两个参数

new Request(input, init)。第三个参数不在签名里，JS 不报错，直接忽略。于是这行的真实语义是：

new Request(req.url, req);   // request 被当成 init

而 Request 实例当作 init 用时，它的 body 是只读流，不能被 init 里的 body 覆盖——即使你写了也无效。结果就是：新 Request 的 body 沿用旧 request 的流，你的 { body: … } 蒸发。

同一条规律也解释了为什么「把 header 改对了但 body 没改」：header 能写、body 不能，因为前者在 init 上是普通字段，后者是流。

三、正确写法：两参数显式 rebuild

const next = new Request(req.url, {
  method: req.method,
  headers: buildHeaders(req.headers),   // 去掉 content-length
  body: JSON.stringify(body),
  signal: req.signal,
  duplex: 'half',                        // Node 18+ 流式 body 必需
  // agent / dispatcher 从原 request 上取不到，需要显式传
});

四条注意：

  1. 删掉 content-length：新 body 长度变了，留着旧值上游会截断或拒绝。
  2. 继承 signal：不继承的话，用户取消请求，你这条新请求还在跑。
  3. Node 需要 duplex: 'half'：body 是流时，缺这个字段直接抛 TypeError: RequestInit: duplex option is required。
  4. agent / dispatcher 要显式带：它们在原始 request 实例上取不到，自定义 keep-alive 或代理配置会静默失效。

四、为什么测试没抓到

改写函数的单元测试断言的是「返回值里 changed === true」，这个断言一直是绿的——因为它测的是改写函数的自述，不是实际发出的字节。

现在的回归测试改成注入一个假 fetchImpl，断言它实际收到的字节：

const seen = [];
await transport('https://api.example.com/v1/chat/completions', {
  method: 'POST',
  body: JSON.stringify({ model: 'x', messages: [{ role: 'user', content: 'hi' }] }),
});

const req = seen[0];
const bytes = await req.arrayBuffer();          // 不是 req.json()
const text = new TextDecoder().decode(bytes);
assert.ok(text.includes('REWRITTEN'), '发出去的字节里必须包含改写后的文本');
assert.ok(!text.includes('content-length: 41'), '不能带旧的 content-length');

用 arrayBuffer() 而不是 json()：json() 会消费流，同一条断言后面再读就是空；字节层面也更容易看出有没有被截断。

五、同类的两个坑

坑表现根因
fetchImpl 是死参数传进去的 fetch 从不被调用，测试全绿但线上走的是 globalThis.fetch参数只做了 typeof 检查，真发包写死全局
dispose 后仍在改写插件卸载了，请求还被动过包装函数没检查 disposed，还原时也没保留原引用

六、四问自查

  1. 新请求是 new Request(url, {…}) 还是 new Request(url, oldReq, {…})？后者无效。
  2. content-length 删了吗？
  3. signal 与 duplex（Node）带了吗？
  4. 测试断言的是返回值，还是假 fetch 收到的字节？
